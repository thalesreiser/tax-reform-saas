# @trs/api

Fastify 5 API: the internal routes used by the web app and the public `/v1` API (BE-03).

| Path             | What it is                                                        |
| ---------------- | ----------------------------------------------------------------- |
| `/health`        | Liveness probe with the deployed version                          |
| `/openapi.json`  | OpenAPI 3.1 document generated from the Zod schemas of each route |
| `/api/auth/*`    | better-auth: sign-up, sign-in, sessions, offices, invitations     |
| `/office`        | Active office of the session and the user's role in it            |
| `/office/audit`  | Audit log of the active office (owner only)                       |
| `/v1/clients`    | Client companies of the office (RF-02)                            |
| `/v1/cnpj/:cnpj` | Registry data of a CNPJ (BrasilAPI)                               |

## Conventions

- **Schemas:** every route declares its params, body and responses with Zod
  (`fastify-type-provider-zod`); types and the OpenAPI document come from them.
- **Errors:** every error response is problem details (RFC 9457, `application/problem+json`) with
  the `requestId`. Validation errors list each field in `errors[]`. A 5xx answer never carries the
  cause; the cause goes to the log.
- **Request id:** always generated by the server (UUID), returned in `x-request-id`; a
  client-supplied id is ignored.
- **Logs:** JSON (pino) with the request id, method, route pattern (never the URL or query
  string), status and duration. `authorization`, `cookie`, `x-api-key` and `set-cookie` are redacted. Never
  log or reflect request bodies: they carry fiscal data, and echoing them is an XSS sink.
- **Errors:** 5xx answers are reported to Sentry when `SENTRY_DSN` is set (`src/sentry.ts`, scrubbed;
  see `deploy/README.md`, Observability).
- **Configuration:** environment variables validated at start-up (`src/config.ts`, `.env.example`).
  An invalid value stops the process with the variable name, never its value.
- **Tests:** `app.inject()` against `buildApp()`, no open port.

## Container

Multi-stage image (`Dockerfile`), built from the repository root:

```sh
docker build -f apps/api/Dockerfile -t trs-api .
docker run --rm -p 3000:3000 -e APP_VERSION=local trs-api
```

- **Base:** `node:24-alpine`, pinned by digest (Dependabot proposes updates). The runtime stage keeps
  only `dist/` and the production dependencies (`pnpm deploy --prod`); npm, Corepack and Yarn are
  removed.
- **User:** runs as the unprivileged `node` user (uid 1000); the application files are owned by root.
- **Environment:** the variables in `.env.example`; the image sets `NODE_ENV=production`,
  `HOST=0.0.0.0` and `PORT=3000`. `APP_VERSION` is set by the deploy pipeline.
- **Health check:** `HEALTHCHECK` calls `GET /health` with Node's `fetch` (no curl in the image).
- **CI:** `.github/workflows/image.yml` builds the image, checks the non-root user, smoke-tests
  `/health` and scans it with Trivy, failing on any critical vulnerability.

Staging runs on Fly.io with Postgres on Supabase: see [`deploy/README.md`](../../deploy/README.md)

## Database

Postgres (Neon in production) through Drizzle ORM on `pg`. Schema: `src/db/schema.ts`; migrations:
`drizzle/` (SQL, committed).

| Command                              | What it does                                                         |
| ------------------------------------ | -------------------------------------------------------------------- |
| `pnpm --filter @trs/api db:generate` | Writes a migration from the schema diff (no database needed)         |
| `pnpm --filter @trs/api db:migrate`  | Applies pending migrations with `DATABASE_MIGRATION_URL` (built API) |
| `pnpm test:integration`              | Database suite; needs a superuser `DATABASE_URL` (CI provides one)   |

### Tenancy and row-level security (RNF-02)

- **Tenant:** `offices`. Every tenant-scoped table has an `office_id` referencing it. An office is
  created (and renamed) only by the trigger on better-auth's `auth_organizations`, with the same
  id, in the same transaction (see Auth).
- **Two roles.** The migrations run as the owner (`DATABASE_MIGRATION_URL`). The API connects with
  `DATABASE_URL` as a login user that is a member of `trs_app`, a role created by the migrations
  that is never superuser, never `BYPASSRLS` and owns no table. Each environment creates its login
  user once: `CREATE ROLE trs_api LOGIN PASSWORD '...' IN ROLE trs_app;`.
- **Policies.** Each tenant table has `ENABLE` and `FORCE ROW LEVEL SECURITY` and a policy
  `office_id = app_current_office_id()` for both reading (`USING`) and writing (`WITH CHECK`).
  `app_current_office_id()` reads the transaction-local setting `app.office_id`; when it is not set
  it is `NULL`, so a query without an office reads zero rows and every write is rejected.
- **`withOffice(db, officeId, fn)`** (`src/db/client.ts`) is the only query path: it validates the
  id, opens a transaction, binds it with `set_config('app.office_id', $1, true)` and runs `fn`. The
  setting ends with the transaction, so a pooled connection never carries an office to the next
  request. `createDb()` returns an opaque handle that exposes nothing else.
- **Superusers and `BYPASSRLS` roles ignore policies.** Never give such a role to the API; owner
  data fixes in a migration see zero rows unless they run as a superuser.
- Never use `drizzle-kit push`: it does not know about the hand-written policies.

### Adding a tenant table

1. Add the table to `src/db/schema.ts` with `officeId: uuid("office_id").notNull().references(() =>
offices.id)`.
2. `pnpm --filter @trs/api db:generate` for the table, then
   `pnpm --filter @trs/api db:generate --custom --name <table>_rls` and write in it (see
   `drizzle/0001_office_rls.sql`): `ENABLE` and `FORCE ROW LEVEL SECURITY`, the `office_isolation`
   policy and the `GRANT` of only the privileges the API needs to `trs_app`.
3. Add isolation cases to `tests/integration/`. The suite fails while any table in `public` lacks a
   forced policy; a table that is deliberately not tenant-scoped (e.g. better-auth's users) goes in
   `NON_TENANT_TABLES` there, with a reason.

## Auth

[better-auth](https://www.better-auth.com) (`src/auth`) on the same Postgres through its Drizzle
adapter (`src/db/auth-schema.ts`, tables `auth_*`), mounted at `/api/auth/*`. Fastify requests are
rebuilt as Web `Request`s on `BETTER_AUTH_URL` (never on the client's `Host`), and its errors are
turned into problem details with better-auth's `code`.

### Flows (RF-01)

1. **Sign-up** `POST /api/auth/sign-up/email` `{ name, email, password }`: e-mail lower-cased,
   password 10 to 128 characters (scrypt). A verification e-mail is sent; sign-in answers 403 until
   the link is followed. Sign-up answers the same for a new and an existing e-mail and never signs
   in, so it does not reveal accounts; sign-in has one error for "unknown e-mail" and "wrong
   password".
2. **Office** `POST /api/auth/organization/create` `{ name, slug }`: a better-auth organization is
   an office. The creator becomes `owner`; a trigger creates the `offices` row with the same id.
3. **Invitation** `POST /api/auth/organization/invite-member` `{ email, role, organizationId }`,
   owner only, role `owner` or `accountant`. The e-mail links to `WEB_URL/convites/<id>`; the id
   (a random UUID) is the secret. It expires after 48 hours, is single-use and only the invited,
   verified e-mail can accept it (`POST /api/auth/organization/accept-invitation`
   `{ invitationId }`), joining the office with the invited role.
4. **Password reset** `POST /api/auth/request-password-reset` `{ email }` e-mails a link to
   `WEB_URL/redefinir-senha?token=<token>` (valid 1 hour, single use); the page posts
   `POST /api/auth/reset-password` `{ token, newPassword }`. The answer is the same whether the e-mail
   exists or not. A reset signs out every session of the user; an expired or used token is a 400 with
   `code: INVALID_TOKEN`.
5. **Active office**: a session starts in the user's oldest office; `organization/set-active`
   switches to another office the user belongs to.

### Roles

| Role         | Can                                                            |
| ------------ | -------------------------------------------------------------- |
| `owner`      | Everything, plus rename the office, invite, remove and re-role |
| `accountant` | Work on the office's data; manages no member or invitation     |

better-auth's default `admin` and `member` roles are rejected by hooks. Offices are never deleted
through the API.

### Tenant bridge

Routes on office data use the `app.requireOffice` preHandler and then
`withOffice(db, currentOffice(request).id, fn)`. It answers 401 (problem details) without a
session and 403 when the session has no active office or the user is no longer a member of it (the
membership is re-read on every request). Row-level security does the rest.

### Cookies, limits and e-mail

- **Session cookie** `trs.session_token` (`__Secure-` prefix in production): signed, `HttpOnly`,
  `SameSite=Lax`, `Secure` in production; better-auth defaults of 7 days, refreshed daily. Requests
  with cookies must come from `BETTER_AUTH_URL` or an allowed origin (origin check, below).
- **CORS** (`@fastify/cors`, `src/origins.ts`): only `WEB_URL` and `CORS_EXTRA_ORIGINS` get CORS
  headers, with credentials, methods `GET`/`POST`, header `content-type`, exposed `retry-after` and
  `x-request-id`, preflight cached 10 minutes. Other origins get none. better-auth's
  `trustedOrigins` uses the same list. `CORS_EXTRA_ORIGINS` takes exact origins and https patterns
  whose `*` starts the host (`https://*-trs-web.thausreiser.workers.dev` for Cloudflare previews):
  the `*` never matches a dot and the fixed part needs three labels, so look-alike hosts and whole
  public suffixes are refused.
- **Cross-site sign-in does not work on staging yet.** `trs-web.thausreiser.workers.dev` and
  `trs-tax-api.fly.dev` are different sites (both `workers.dev` and `fly.dev` are public suffixes),
  so the browser never sends the `SameSite=Lax` session cookie on the web app's `fetch` calls (and
  blocks it as third-party). CORS works; sessions do not. Options under Pending.
- **Rate limits** (`@fastify/rate-limit`, in memory per process): 120 requests per minute per IP on
  `/api/auth/*`; sign-in, sign-up, verification e-mails, password-reset requests and submissions
  30 per IP and 5 per e-mail in 15 minutes,
  then 429 with `Retry-After`. better-auth's own limiter is off (it keys on IP headers only).
- **E-mail** goes through the `Mailer` interface. Only `LogMailer` exists: outside production it logs
  the whole message (follow links from the log); in production it logs only the subject, never the
  link or the address. No real provider yet: production cannot send e-mails.

### Pending

- E-mail provider (blocks production sign-up, invitations and password reset; Resend recommended).
- **Session cookie across sites** (blocks real sign-in from the web app):
  1. **Own domain (recommended):** `app.<domain>` on Cloudflare and `api.<domain>` on Fly, with
     better-auth `crossSubDomainCookies` on `<domain>`. Same site, so `SameSite=Lax` keeps working,
     SSR sees the session and no third-party cookie is involved. Needs a domain and DNS.
  2. **`SameSite=None; Secure` cookies** on the current hosts: works today in some browsers only;
     Safari and Chrome's third-party cookie restrictions block them unless partitioned (CHIPS
     `Partitioned`), which ties the cookie to the web site and still hides it from SSR. Weaker CSRF
     defence (origin check only). Not done here.
- Session lifetime, 2FA, social login, roles beyond owner and accountant.
- Shared rate-limit store (database or Redis) with more than one API instance, and `trustProxy`
  once the host is known, so limits see the client IP.
- Web routes for e-mail links (`/convites/<id>`, verification callback): FE-01.3.

## Audit log

Append-only log of actions per office (RF-18), table `audit_events` (`0004_audit_events.sql`, RLS
and append-only rules in `0005_audit_events_rls.sql`).

### What is logged

| Action                                                     | Resource   | Metadata                    |
| ---------------------------------------------------------- | ---------- | --------------------------- |
| `office.created`                                           | office     | none                        |
| `office.updated`                                           | office     | names of the fields sent    |
| `member.invited`                                           | invitation | invited role                |
| `member.invitation_canceled`, `member.invitation_rejected` | invitation | none                        |
| `member.joined`                                            | member     | role, invitation id         |
| `member.role_changed`                                      | member     | previous and new role       |
| `member.removed`, `member.left`                            | member     | role                        |
| `client.created`, `client.updated`, `client.deleted`       | client     | names of the fields changed |

Every event has the office, the actor (user id and role in the office; null for the system), the
time (`occurred_at`, set by Postgres) and the `x-request-id` of the request. The `client.*` actions
are ready for the client routes (BE-02.2); API keys and simulations add their actions the same way.

### What is never logged

Names, e-mails, CNPJs, fiscal values or any free text. Metadata is validated against a Zod
allow-list per action (`src/audit/events.ts`) that holds only enums, ids and field names; a unit test
fails if an action declares anything else. The column is also limited to a 1 KB JSON object.

### Writing an event

Inside the transaction of the action, so both commit or roll back together:

```ts
await withOffice(db, office.id, async (tx) => {
  const [client] = await tx.insert(clients).values(values).returning()
  await recordAudit(tx, {
    action: "client.created",
    resourceId: client.id,
    metadata: {},
    ...auditContext(request), // actor and request id, from app.requireOffice
  })
})
```

A new action is a value in `AUDIT_ACTIONS` (`src/db/schema.ts`, then `db:generate`) plus its
metadata schema and resource type in `src/audit/events.ts`.

better-auth's office, member and invitation actions are recorded by its organization after-hooks
(`src/audit/auth-hooks.ts`). better-auth commits its own write before those hooks run, so that event
is written right after the action in a separate transaction: if the event cannot be written, the
request answers 500 but the action stands. `organization/leave` has no hook and is recorded by the
auth route after it succeeds.

### Access and retention

- **Append-only:** `trs_app` has `SELECT` and `INSERT` only, and triggers reject `UPDATE`, `DELETE`
  and `TRUNCATE` for every role, the owner included. Row-level security isolates offices.
- **`GET /office/audit`:** owner only (accountants get 403). Newest first; `action`, `from`
  (inclusive) and `to` (exclusive) filters; `limit` 1 to 100 (default 50); `cursor` from the
  previous page's `nextCursor`.
- `actor_user_id` has no foreign key, so a deleted user's events stay.

### Pending

- Retention period (kept forever for now) and what happens to a deleted user's events (LGPD,
  BE-05.1).
- Whether accountants may read the log.

## Reference data

`GET /v1/reference/...` (RF-13) serves the reference tables of the official regime-regular engine
through `@trs/engine-client`. Every route requires a signed-in office session for now (`requireOffice`;
API keys come with BE-03.1 as a second entry in the plugin's `authenticate` list).

| Route                         | Engine source                                          |
| ----------------------------- | ------------------------------------------------------ |
| `/cst`                        | CSTs with their cClassTrib (`situacoes-tributarias`)   |
| `/class-trib/:code`           | One cClassTrib                                         |
| `/legal-bases`                | Legal basis of each CST/cClassTrib                     |
| `/ncm`, `/nbs`                | Search (`q`: code prefix or words), `page`, `pageSize` |
| `/ncm/:code`, `/nbs/:code`    | One NCM / NBS                                          |
| `/rates/union`                | CBS reference rate                                     |
| `/rates/states/:code`         | IBS state rate (IBGE UF code)                          |
| `/rates/municipalities/:code` | IBS municipal rate (IBGE code)                         |

- Every route takes `date` (YYYY-MM-DD, default today in Brasília) and answers
  `{ engine: { name, version }, dataVersion: { version, date }, validOn, data }`; decimals are text.
- **Cache.** In-process LRU (`lru-cache`) keyed by engine version, endpoint and normalised parameters,
  for `REFERENCE_CACHE_TTL_SECONDS` (default 6 h); the engine version itself is re-read every 5 min.
  Concurrent misses share one engine call; failures are not cached. Answers carry
  `Cache-Control: private, max-age=<ttl>` and an `ETag`; a matching `If-None-Match` gets 304.
- **Errors.** No `ENGINE_REGIME_REGULAR_URL`: 503. Engine timeout (`ENGINE_TIMEOUT_MS`, default 30 s
  for a Flycast cold start): 504. Engine 404: 404. Other failures: 502. Details are generic; the
  engine body is never returned or logged, and the request log shows the route pattern, not the codes.

## Office

Settings and members of the active office (BE-02.1, RF-01), all behind `app.requireOffice`. Any
member reads; only owners write (403 otherwise). Every change is audited with ids, roles and field
names only, never names, e-mails or other values.

| Route                                    | Who   | What it does                                                   |
| ---------------------------------------- | ----- | -------------------------------------------------------------- |
| `GET /v1/office`                         | all   | Name, CNPJ, contact, brand colour with its contrast, logo info |
| `PATCH /v1/office`                       | owner | Change `name`, `cnpj`, `contactEmail`, `contactPhone`, colour  |
| `GET /v1/office/logo`                    | all   | The logo, with `ETag` (`If-None-Match` answers 304)            |
| `POST /v1/office/logo`                   | owner | Upload: the image is the body (`image/png`, `jpeg` or `webp`)  |
| `DELETE /v1/office/logo`                 | owner | Remove the logo                                                |
| `GET /v1/office/members`                 | all   | Members with name, e-mail and role                             |
| `PATCH /v1/office/members/:id`           | owner | Change the role (`owner` / `accountant`)                       |
| `DELETE /v1/office/members/:id`          | owner | Remove; their access ends on the next request                  |
| `GET /v1/office/invitations`             | owner | Pending, unexpired invitations                                 |
| `DELETE /v1/office/invitations/:id`      | owner | Cancel                                                         |
| `POST /v1/office/invitations/:id/resend` | owner | Send the e-mail again and extend it by 48 hours                |

- **Name:** renames the better-auth organization; the trigger of `0003_auth_rls.sql` renames the
  office in the same transaction. **CNPJ** is the office's own, validated like clients'.
- **Brand colour:** `#RRGGBB` (stored upper-case). `brandContrast` gives the WCAG contrast ratio
  against white and black and whether each meets AA (4.5:1), so the web app can warn.
- **Logo:** PNG, JPEG or WebP, detected from the bytes (the declared type must match), at most
  200 KB, 16 to 2048 pixels per side. SVG is rejected (it can carry scripts). Stored in Postgres
  (`office_logos`, `bytea`, row-level security) until an object storage provider exists; served with
  `Cache-Control: private, no-cache`, `ETag`, `nosniff` and `default-src 'none'`.
- **Members and invitations** go through better-auth's organization API, so its checks and audit
  hooks apply; ids of another office answer 404. Removing or demoting the last owner answers 409.
  Removal also clears the office as the active office of that user's sessions.
- Migration `0008_office_settings.sql`: office columns, `office_logos` with its policy and grants,
  and the `member.invitation_resent` audit action.

## Clients

Client companies of the office (RF-02), table `clients` (registry columns and the CNPJ `CHECK` in
`0007_client_registry.sql`; row-level security from `0001_office_rls.sql`). Owners and accountants
have the same access.

| Route                    | What it does                                                        |
| ------------------------ | ------------------------------------------------------------------- |
| `GET /v1/cnpj/:cnpj`     | Registry data of a CNPJ: names, address, CNAEs, status, Simples/MEI |
| `POST /v1/clients`       | Create; `lookup: true` fills the registry fields (sent names win)   |
| `GET /v1/clients`        | List: `q` (part of a name or start of the CNPJ), `page`, `pageSize` |
| `GET /v1/clients/:id`    | One client                                                          |
| `PATCH /v1/clients/:id`  | Change `legalName`, `tradeName` or `notes`                          |
| `DELETE /v1/clients/:id` | Hard delete (the audit events stay)                                 |

- **CNPJ** (`src/clients/cnpj.ts`): numeric and alphanumeric (from July 2026: 12 characters `0-9A-Z`
  and 2 numeric check digits, modulo 11 over ASCII - 48, Receita Federal technical note). Input may be
  masked and lowercase; it is stored normalised. The database only checks the format
  (`^[0-9A-Z]{12}[0-9]{2}$`); the API checks the digits. A CNPJ is unique per office (409).
- **Audit:** every create, update and delete writes `client.*` in the same transaction; updates list
  only the names of the fields sent.
- **Regime:** `mei` or `simples_nacional` only when the registry says so, otherwise `unknown`; the
  latest yearly taxation form the registry reports is returned as given, never inferred.
- **Logs:** CNPJs and search text never reach the log (the request log shows the route pattern).

### CNPJ provider

**Decided (Thales, 2026-11-24): BrasilAPI** (`https://brasilapi.com.br/api/cnpj/v1/{cnpj}`) for
staging and beta. It is a free third-party service **without SLA**, to be revisited before production
(e.g. a paid provider or the Receita's own data). The provider sits behind the `CnpjProvider`
interface (`src/clients/lookup.ts`), so replacing it is one module.

- `CNPJ_LOOKUP_URL` and `CNPJ_LOOKUP_TIMEOUT_MS` (default 8 s). In-process LRU cache (1 h, 500
  entries, shared by offices: registry data is public); failures are not cached.
- 30 lookups per office per minute (also counted for `POST /v1/clients` with `lookup: true`): 429.
- Errors: not in the registry 404 (422 on create); timeout 504; any other failure 502. Details are
  generic; the provider's body is never returned or logged.
- BrasilAPI may not know alphanumeric CNPJs yet: those lookups answer 404/502 until it does, and the
  client can still be created by hand.
