# 004 - Official engines: build and runtime

- **Status:** proposed
- **Date:** 2026-11-23
- **Decided by:** pending (Thales Reiser)
- **Reference:** MOT-01.1, RNF-01, feeds DEC-01 (hosting)

## Context

ADR 001 runs the Receita Federal engines unmodified as sidecars. Before building images (MOT-01.2)
and choosing a host (DEC-01), we needed to know whether both engines build from a release tag in CI,
how they get their database, how long they take to start and how much memory they need.

Pinned tags: `calculadora-rtc-regime-regular` **1.7.2** and `calculadora-rtc-simples-nacional`
**1.0.2** (`engines/versions.env`). Workflow: `.github/workflows/engines.yml`.

Findings from upstream:

- Both are Java 25 / Spring Boot 4.1 jars built with the Maven wrapper, which downloads Maven 3.9.5
  and every dependency from Maven Central: the build needs internet (fine in CI, not in an
  air-gapped image build).
- The `offline` profile opens `./calculadora/db/calculadora-pro.db` read-only, relative to the
  working directory. The file is generated by Flyway from the SQL scripts in the regime-regular
  repository (73 migrations at 1.7.2, about 6 MB). The Simples repository has no scripts; its
  README says to use the regime-regular ones, so both engines share one database file built from
  the regime-regular tag.
- Ports: regime-regular HTTP 8080 (`/api/calculadora/...`), management 9101 (`/health`,
  `/metrics`); Simples HTTP 8082 (`/api/...`), management 9103.
- The SQLite driver extracts a native library at start-up, so the container needs a writable
  temporary directory (`/tmp` or `-Dorg.sqlite.tmpdir`). JDK 25 prints "restricted method" and
  `sun.misc.Unsafe` warnings from the driver and from ModelMapper; they are harmless today.
- The upstream Simples `docs/exemplos.md` is a copy of the regime-regular one; the Simples smoke test
  uses the NF-e example from its OpenAPI contract (`EXEMPLO_NFE`) with the values its own integration
  test asserts (vCBSSN 11.61, vIBSSN 0.13).
- Swagger UI and `/api-docs` are enabled in the offline profile: the engines must stay on a private
  network, reachable only by our API.

## Measurements

GitHub-hosted `ubuntu-latest` runner (4 vCPU, 16 GB), Temurin 25.0.5, run of 2026-11-23 with a warm
Maven cache. "Healthy after" is from `java -jar` to `/health` answering 200. RSS is the process
resident set after start-up, after the example plus 50 more requests, and the peak (`VmHWM`).
Each run also checked the official example: all passed.

Build (per engine job, about 1.5 min end to end):

| Step                              | Regime regular | Simples Nacional |
| --------------------------------- | -------------- | ---------------- |
| Flyway database (cold Maven)      | 15 s           | 13 s             |
| Flyway database (warm Maven)      | 7 s            | 7 s              |
| `mvnw package -DskipTests` (cold) | 20 s           | 13 s             |
| `mvnw package -DskipTests` (warm) | 16 s           | 11 s             |
| Jar size                          | 88 MB          | 82 MB            |

Runtime, regime-regular 1.7.2:

| JVM options                                                    | Max heap | Healthy after | Spring start | RSS idle | RSS after load | Peak RSS | Warm request |
| -------------------------------------------------------------- | -------- | ------------- | ------------ | -------- | -------------- | -------- | ------------ |
| none (sized to the 16 GB host)                                 | 3996 MB  | 16.5 s        | 12.5 s       | 718 MB   | 784 MB         | 784 MB   | 31 ms        |
| `-XX:MaxRAM=512m -XX:MaxRAMPercentage=75 -XX:+UseSerialGC`     | 384 MB   | 14.8 s        | 12.1 s       | 450 MB   | 489 MB         | 489 MB   | 31 ms        |
| same + `-XX:TieredStopAtLevel=1 -XX:ReservedCodeCacheSize=64m` | 384 MB   | 15.2 s        | 12.2 s       | 377 MB   | 408 MB         | 408 MB   | 23 ms        |

Runtime, simples-nacional 1.0.2:

| JVM options                                                    | Max heap | Healthy after | Spring start | RSS idle | RSS after load | Peak RSS | Warm request |
| -------------------------------------------------------------- | -------- | ------------- | ------------ | -------- | -------------- | -------- | ------------ |
| none (sized to the 16 GB host)                                 | 3996 MB  | 15.1 s        | 11.5 s       | 493 MB   | 518 MB         | 518 MB   | 28 ms        |
| `-XX:MaxRAM=512m -XX:MaxRAMPercentage=75 -XX:+UseSerialGC`     | 384 MB   | 13.9 s        | 10.3 s       | 390 MB   | 408 MB         | 408 MB   | 26 ms        |
| same + `-XX:TieredStopAtLevel=1 -XX:ReservedCodeCacheSize=64m` | 384 MB   | 13.5 s        | 10.6 s       | 327 MB   | 351 MB         | 351 MB   | 24 ms        |

The 512 MB rows also use `-Xss512k`. `-XX:MaxRAM=512m` makes the JVM size itself as in a 512 MB
container; it does not enforce the limit. A real cgroup limit is tested in MOT-01.2.

Reading the numbers:

- Start-up is about 15 s for either engine on 4 vCPU; expect more on a 1 or 2 vCPU host. Health
  checks need a start period of at least 60 s.
- With the default sizing the JVM keeps what it touched: 0.5 to 0.8 GB per engine. Constrained, the
  regime-regular engine peaks near 490 MB, too close to a 512 MB limit once heap grows under real
  load; the Simples engine fits with about 100 MB to spare.
- C1-only saves about 70 to 80 MB per engine at no visible cost for this light load; peak
  throughput under sustained load was not measured.

## Options considered

1. **Build unmodified from the pinned tag in CI, run the jar with tuned JVM flags:** exact official
   behaviour, upgrades are a tag bump, no fork to maintain. Cost: about 1.5 min of CI per engine
   and a JVM per engine.
2. **Fork the engines to slim them down** (drop Swagger, tracing, unused endpoints): less memory,
   but it breaks "never modified" and every upstream release becomes a merge.
3. **Use upstream images or jars:** the upstream READMEs reference none for these tags, so not
   available today; to revisit if Receita Federal starts publishing them.

## Decision

Proposed: option 1. Run both engines unmodified, pinned to a tag and commit in
`engines/versions.env`, built from source in CI, with the shared database generated by Flyway from
the regime-regular tag. For the container host (DEC-01) plan for:

- **768 MB per engine** with `-XX:MaxRAMPercentage=75 -XX:+UseSerialGC -Xss512k` (heap derived from
  the container limit), about **1.5 GB for both engines**, plus the API;
- 512 MB per engine only with the C1-only flags and after MOT-01.2 confirms it under a real limit;
- a writable `/tmp`, the database file in the image at `./calculadora/db/`, ports on a private
  network only, and a health-check start period of at least 60 s.

Awaiting Thales's acceptance.

## Consequences

- MOT-01.2 builds one image per engine from the jar and database this workflow produces, runs it
  with the flags above under a real memory limit and repeats the smoke test.
- DEC-01: a VPS or managed plan needs about 2 GB RAM for the two engines and the API; 1 vCPU
  plans will start slower.
- MOT-01.4 bumps tag and SHA together; the weekly workflow run already catches upstream or runner
  breakage at the pinned tag.
- Every stored result records the engine tag from `versions.env`; the database version comes with
  it, because the database is built from the regime-regular tag.
